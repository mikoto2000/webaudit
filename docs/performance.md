# 性能測定

現行のv2.0.2を基準にした高速化前後の比較は、末尾の「2026-11-25: 分析処理の高速化」を参照してください。

以下の表は0.1.0の履歴です。0.2.0の上流互換エンジンを含む測定は[上流互換性](upstream-compatibility.md)および`measurements/upstream/performance-*.json`を参照してください。ルール数と既定の重複処理が変わっているため、旧版の速度を現行版の速度として扱わないでください。

2026-11-20、Windows amd64、Go 1.27.4、24論理CPU。合成ログ生成を計測区間から外し、ファイルを閉じた後に `audit.Analyze` の全パイプラインを測定しました。16個の接続元・32パスで、時刻とnonceを変え、重複除外で処理が短縮されないようにしています。巨大ケースはUAに3000bytesのパディングを追加しています。

再現: `go run ./tools/benchmark -lines 1000000`、大容量版は `-padding 3000` を追加。キャッシュ状況・ディスク・CPU・ルール・カーディナリティで変動する単発測定です。OSのファイルキャッシュは統制していません。

| 行数 | 入力bytes | 秒 | 行/秒 | ピークGoヒープbytes | ピークWorking Set bytes |
|---:|---:|---:|---:|---:|---:|
| 100,000 | 11,001,390 | 2.72 | 36,821 | 4,008,664 | 16,859,136 |
| 1,000,000 | 111,013,890 | 25.75 | 38,834 | 5,048,088 | 17,813,504 |
| 1,000,000 | 3,111,013,890 | 106.37 | 9,401 | 8,331,424 | 22,384,640 |

各ケースは全行を解析し、解析不能0・重複0・部分解析falseでした。高頻度のためrate/burst候補は生成されています。100万行・約3.11GBの入力を実測で処理できました。全ログのメモリ読込やgzipのディスク展開は行っていません。大容量の実測入力は非圧縮です。gzipは機能・破損CRC・展開量上限のテストで確認し、GB級gzipの性能は未計測です。

Goヒープは10ms間隔のHeapAllocの最大観測値で、厳密な最大やプロセス全メモリではありません。Working SetはWindows GetProcessMemoryInfoを1秒間隔で呼び、OSのPeakWorkingSetSizeを取得したものです。生成フェーズも含みます。総割当量は再利用前の累計であり、保持メモリではありません。初回・後続のOSページングによる差があります。

固定カーディナリティの10万→100万行で保持メモリは件数に比例して増えていません。ただし、任意のIP・URL・時間区間が増えるログに対する一定メモリでの完全解析を証明したものではありません。初期版は各表4096キー、異なる値64、事案・シグナル各2000、事案証拠32MiB、1事案8サンプルに制限します。上限時には警告と部分解析状態を返し、新しい状態を保持できないため検出漏れがあり得ます。上限を上げる場合は使用メモリも増加します。

今後の改善候補は、圧縮・高カーディナリティ・長期間・乱順入力での独立測定、ディスクを使った外部ソート/集約、サイズ基準値の更新コストと割当の削減です。計測用ログは一時ファイルとして生成し、終了時に削除します。機械可読の実測値は measurements/performance-*.json に保存しています。

## 2026-11-25: 分析処理の高速化

v2.0.2のコミット`a4b73ff`を基準に、次の4候補を適用しました。

- Aura署名と独自ルールに、正規表現の構文木から得た必須文字列による事前選別を追加。選択肢がある場合は全分岐に必要な文字列が得られるときだけ選別し、通過した候補は元のRE2で判定します。
- 大文字小文字を無視するリスト照合の固定パターンを、初期化時に大文字化して保持。
- 独自ルールで使うURL変種・UA・Refererなどの小文字化を、ルール間で共有。
- オンライン応答サイズ統計の中央値・MAD計算に、Analysisごとの128要素の作業領域を再利用。毎観測の正確な中央値・MAD、観測順、閾値を維持します。

Unicodeや不正UTF-8を含むフィールドは事前選別を省略し、RE2に直接渡します。この入力ではASCII中心の測定と同じ改善率を期待できません。

Windows amd64、Go 1.27.4、24論理CPU。変更前にも変更後と同一の計測コードを配置し、ビルド・ログ生成・レポートハッシュ計算を計測区間から外して`audit.Analyze`を測りました。各条件は独立プロセスで前後を交互に実行し、2回目は順序を反転、各3回の中央値を比較しています。測定中はテストや別のベンチマークを同時実行していません。CPUプロファイラは無効、OSファイルキャッシュは未統制です。

| 条件 | 行数 | 変更前 秒 | 変更後 秒 | 速度比 | 累計割当量の削減率 |
|---|---:|---:|---:|---:|---:|
| 通常 | 100,000 | 23.055 | 4.079 | 5.65倍 | 78.6% |
| UAに3000bytes追加 | 10,000 | 4.605 | 2.523 | 1.82倍 | 27.4% |
| 20%攻撃混在 | 10,000 | 2.721 | 0.957 | 2.84倍 | 75.9% |

通常10万行の解析区間の累計割当量は、中央値で1,758,004,368bytesから376,767,840bytesに減少しました。累計割当量は保持メモリやOSのRSSではありません。各回の時間、割当回数、サンプルヒープ、警告、レポートハッシュは[測定生データ](measurements/analysis-optimization.json)に保存しています。単一開発機の合成ログ測定であり、実ログ・gzip・GeoIP有効時・bundle生成全体の改善率は未計測です。

3条件とも全行をパースし、前後・全反復でレポートのSHA-256が一致しました。解析日時を固定し、一時入力ディレクトリだけ正規化して比較しています。長いUAの条件は、既存仕様のUAサンプル切り詰めで前後とも`partial=true`となり、同じ警告を保持します。通常・攻撃混在は`partial=false`です。

加えて、既存コーパス71件・上流互換用ログ107件・サンプル2件の計180件で、CLIのJSONレポート全体を比較しました。解析日時を除外し、既存のmap走査順に依存するトップレベル警告の並びだけそろえ、それ以外は一致しています。[照合結果](measurements/analysis-optimization-parity.json)に各ケースの件数とハッシュを保存しています。

検証は`go test ./...`、`go vet ./...`、`go run ./tools/evaluate`、Windows CLIビルド、`FuzzSourcePattern`の20秒実行（4,487回）で通過しました。追加テストは、全署名の分岐に対応する文字列・Unicode・不正UTF-8とRE2との判定一致、リスト照合の一致、サイズ基準のリング更新と判定一致・割当ゼロを確認します。Linuxのrace・seccomp検証はローカルでは実行していません。

再現には、変更前worktreeにも変更後の`tools/benchmark/main.go`だけをコピーし、計測器を同一にしてから各worktreeでビルドしてください。

```sh
# 変更前・変更後の各worktreeで、異なる出力先にビルド
go build -o /absolute/path/to/before-or-after ./tools/benchmark

# 変更後worktreeから前後の実行ファイルを指定
python tools/compare-performance.py --before /absolute/path/to/before --after /absolute/path/to/after --output comparison.json
```

比較スクリプトは3条件を各3回逐次実行し、全行パースとレポートハッシュ一致を確認したうえで中央値を出力します。単体測定は`go run ./tools/benchmark -lines 100000`、長いUAは`-lines 10000 -padding 3000`、攻撃混在は`-lines 10000 -mixed`です。
