# 性能測定

以下の表は0.1.0の履歴です。0.2.0の上流互換エンジンを含む測定は[上流互換性](upstream-compatibility.md)および`measurements/upstream/performance-*.json`を参照してください。ルール数と既定の重複処理が変わっているため、旧版の速度を現行版の速度として扱わないでください。

2026-11-20、Windows amd64、Go 1.27.4、24論理CPU。合成ログ生成を計測区間から外し、ファイルを閉じた後に `audit.Analyze` の全パイプラインを測定しました。16個の接続元・32パスで、時刻とnonceを変え、重複除外で処理が短縮されないようにしています。巨大ケースはUAに3000bytesのパディングを追加しています。

再現: `go run ./tools/benchmark -lines 1000000`、大容量版は `-padding 3000` を追加。キャッシュ状況・ディスク・CPU・ルール・カーディナリティで変動する単発測定です。OSのファイルキャッシュは統制していません。

| 行数 | 入力bytes | 秒 | 行/秒 | ピークGoヒープbytes | ピークWorking Set bytes |
|---:|---:|---:|---:|---:|---:|
| 100,000 | 11,001,390 | 2.72 | 36,821 | 4,008,664 | 16,859,136 |
| 1,000,000 | 111,013,890 | 25.75 | 38,834 | 5,048,088 | 17,813,504 |
| 1,000,000 | 3,111,013,890 | 106.37 | 9,401 | 8,331,424 | 22,384,640 |

各ケースは全行を解析し、解析不能0・重複0・部分解析falseでした。高頻度のためrate/burst候補は生成されています。100万行・約3.11GBの入力を実測で処理できました。全ログのメモリ読込やgzipのディスク展開は行っていません。大容量の実測入力は非圧縮です。gzipは機能・破損CRC・展開量上限のテストで確認し、GB級gzipの性能は未計測です。

Goヒープは10ms間隔のHeapAllocの最大観測値で、厳密な最大やプロセス全メモリではありません。Working SetはWindows GetProcessMemoryInfoを1秒間隔で呼び、OSのPeakWorkingSetSizeを取得したものです。生成フェーズも含みます。総割当量は再利用前の累計であり、保持メモリではありません。初回・後続のOSページングによる差があります。

固定カーディナリティの10万→100万行で保持メモリは件数に比例して増えていません。ただし、任意のIP・URL・時間区間が増えるログに対する一定メモリでの完全解析を証明したものではありません。初期版は各表4096キー、異なる値64、事案・シグナル各2000、事案証拠32MiB、1事案8サンプルに制限します。上限時には警告と部分解析状態を返し、新しい状態を保持できないため検出漏れがあり得ます。上限を上げる場合は使用メモリも増加します。

今後の改善候補は、圧縮・高カーディナリティ・長期間・乱順入力での独立測定、ディスクを使った外部ソート/集約、サイズ基準値の更新コストと割当の削減です。計測用ログは一時ファイルとして生成し、終了時に削除します。機械可読の実測値は measurements/performance-*.json に保存しています。
